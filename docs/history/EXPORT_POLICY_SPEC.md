# Export / Storage Policy Specification

**Date:** 2026-03-09  
**Scope:** Define canonical dataset outputs vs optional user exports. No runtime code changes in this step.

---

## 1. PURPOSE

- **Goal:** Simplify the storage model and reduce clutter without breaking the deterministic workflow.
- Separate two concepts: (1) **canonical outputs** that the pipeline must always generate and store after RUN (audit trail, reproducibility, downstream tooling), and (2) **optional user exports** that are copied into `exports/` only when the user explicitly requests them via the Export tab.
- This clarifies what belongs in analysis storage by default and what is “takeaway” material for the user, and keeps `exports/` from being used as default analysis storage.

---

## 2. CURRENT STATE

- **Where outputs are stored:** After an OT RUN, all pipeline outputs are written under the run directory (dataset mode: `item_root/analysis/`; batch mode: `item_root/module/ot/`). Files are then organized into subdirs: `audit/` (postprocess, psd_fit, calibration JSONs), `tracking/` (trajectory CSV, PNGs), `physics/` (MSD, PSD, calibration CSV, histograms, derived, compare, drag). `run.json`, `_results.csv`, and `_results.xlsx` remain in the run root.
- **Artifact types in practice (OT):**
  - **JSON:** `run.json`, `*_postprocess.json`, `*_psd_fit.json`, `*_calibration.json`, `*_camera_meta.json`, `*_qc.json`, `*_ot_summary.json`, `run_manifest.json`, `*_compare.json`, `*_drag.json`.
  - **XLSX:** `*_results.xlsx` (from `export_ot_results_xlsx`).
  - **CSV:** trajectory, tracking, PSD, calibration, MSD, histograms, derived, results, compare.
  - **PNG:** after, after_raw, preview_tracking, QC/strategy plots.
- **Duplication:** There is no automatic copy from analysis to `exports/`. The `exports/` directory is created (e.g. `item_root/exports` in dataset mode) but is only populated when the user clicks EXPORT in the Export tab; the Export action copies user-selected artifacts from the analysis tree into `exports/`. So duplication is “same logical file in analysis vs a user-requested copy in exports,” not automatic double-writing by the pipeline.

---

## 3. TARGET POLICY

- **All `.json` outputs** are canonical and must be generated and stored by default (RUN). They are part of the audit trail and reproducibility; they are not optional export-only.
- **All `.xlsx` outputs** are canonical and must be generated and stored by default (RUN). They are the human-facing bundle produced by the pipeline.
- **Other artifacts** (e.g. `.csv`, `.png`, and similar analysis byproducts) are **optional export artifacts** unless explicitly required elsewhere (e.g. a downstream step that must read a specific CSV). They may be generated by RUN and stored under the analysis tree, but they are not “canonical” in the sense of “must always be present for pipeline correctness”; they are candidates for user export.
- **`exports/`** must represent **explicit user export output**, not default analysis storage. Nothing is written into `exports/` by the RUN itself.
- **`exports/`** should only be created and populated when the user runs EXPORT (Export tab → EXPORT button). The pipeline must not write canonical outputs into `exports/` by default.

## 5. EXPORT UI POLICY

- **Export tab shows only optional export artifacts.** Canonical JSON and XLSX are not listed as export targets; they already live in the analysis tree. The Export tab lists only artifacts classified as OPTIONAL EXPORT (e.g. trajectory CSV, other CSVs, QC report copy, PNGs) so the user chooses what to copy into `exports/`.
- **Add “Select All”:** A control that checks all visible optional-export checkboxes in the Export tab.
- **Add “Clear All”:** A control that unchecks all visible optional-export checkboxes.
- **Default checked behavior:** When the Export tab is populated with optional export artifacts, the default is **all checked** (current behavior). If policy later changes to “none checked by default,” that must be explicitly specified and implemented in one step.
- **Export button enable rule:** The EXPORT button is enabled when (1) at least one optional export artifact is discovered for the current dataset, and (2) at least one checkbox is checked. If no artifacts are discovered, or all are unchecked, the button is disabled.

---

## 6. NON-GOALS

The following are **not** changed in this policy step:

- No dataset schema rename.
- No broad refactor of pipeline or UI.
- No experiment registry redesign.
- No AI/computation logic changes.
- No physics or calibration logic changes.
- No change to where RUN writes files (analysis/ or module/ot/); only the classification and Export tab behavior are specified.

---

## 7. SAFE IMPLEMENTATION ROADMAP

1. **Artifact classification backend:** In discovery (or a small policy module), classify each discovered artifact as canonical vs optional export. Expose “optional export only” list to the Export tab (e.g. discovery returns only optional-export artifacts, or discovery returns all and a filter restricts the Export tab to optional only).
2. **Export tab filtering:** Wire the Export tab to show only optional export artifacts (using the classification from step 1). Ensure canonical JSON/XLSX are never offered as export checkboxes.
3. **Select All / Clear All:** Add Select All and Clear All controls to the Export tab; wire them to check/uncheck all visible artifact checkboxes.
4. **Export execution alignment:** Ensure the Export action copies only optional-export artifacts into `exports/` and uses the same paths/ids as the Export tab (no copying of run.json or _results.xlsx via Export tab; they remain only in the analysis tree).
5. **Optional later cleanup:** Optionally document or implement cleanup of empty `exports/` folders or redundant copies in a later step, without changing schema or canonical output locations.
